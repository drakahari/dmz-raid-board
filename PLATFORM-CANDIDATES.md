# Native platform candidates

Previous releases remain unchanged. Version 0.1.5 uses the same native packaging and storage fixes, adds version metadata and item-only views, and drops Intel Mac builds. The candidate-branch `Native platform candidates` workflow prepares separate macOS Apple Silicon and Linux x64 candidates from its exact recorded commit. These are workflow artifacts, not automatically published platform releases or native owner acceptance.

The app remains Electron with the same UI, local artwork and themes. It does not require an external browser. Windows packaged builds keep portable data beside the executable. macOS and Linux leave Electron's normal per-user user-data path intact (under Application Support on macOS and the configured application-data directory on Linux), outside a read-only app bundle or AppImage mount. Explicit isolated QA profile paths remain supported. Version-1 board backups stay compatible.

Only standard GitHub-hosted public-repository runners are used: macos-15 arm64 and ubuntu-22.04 x64. Official actions are pinned by full commit SHA. The workflow runs only on pushes to platform-candidates or release-0.1.5 (with an optional dispatch hook for future default-branch registration), has read-only repository permissions, does not create credentials or publish releases, and retains artifacts for three days. See [runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

Artwork is reused only from the already-published, owner-approved Windows v0.1.4 ZIP with its exact SHA256 checked. No source-site images are downloaded. Every extracted image is checked against the bundled sanitized inventory; existing local files are never silently replaced. The same game-art rights notices and DLMS/Omarchy MIT notices accompany candidates.

macOS targets are app ZIP and DMG, ad-hoc signed without a Developer ID identity, signing service or notarization. They are not trusted signed/notarized distributions; Gatekeeper and native owner acceptance remain pending. No system-security workaround is included. Linux targets AppImage; automated launch uses its supported extract-and-run mode under Xvfb, without changing kernel/AppArmor settings or passing --no-sandbox. FUSE mounting and validation on an owner's desktop/distribution remain pending.

A successful workflow artifact includes native-test.json describing the actual native-runner launch, secure renderer, writable per-user storage, editable target/Settings/theme behavior, metadata version, old-backup import, item-only catalog and packaged icon resources and real process relaunch persistence, plus checksums and a synthetic app screenshot. Binaries are staged only after smoke checks pass. Build success alone is not native user acceptance. Each candidate records its exact source commit; a candidate built after the Windows tag is not claimed to be that tag's Windows binary.

Version 0.1.6 candidates run from fix/recipe-target-baselines as well. The full target acceptance suite runs against each native packaged app using an isolated QA profile: empty first use, automatic recipe baselines, shared totals, extras, removals, recovery-safe clear/restore, legacy zero migration, hidden completion messaging and real process relaunch. Version-2 storage preserves the legacy board separately; see docs/target-planning.md. These artifacts are candidates and are not automatically uploaded to a public GitHub release.
