# Native platform candidates

The published Windows v0.1.4 prerelease remains unchanged. The candidate-branch `Native platform candidates` workflow prepares separate macOS Apple Silicon, macOS Intel and Linux x64 candidates from its exact recorded commit. These are workflow artifacts, not automatically published platform releases or native owner acceptance.

The app remains Electron with the same UI, local artwork and themes. It does not require an external browser. Windows packaged builds keep portable data beside the executable. macOS and Linux leave Electron's normal per-user user-data path intact (under Application Support on macOS and the configured application-data directory on Linux), outside a read-only app bundle or AppImage mount. Explicit isolated QA profile paths remain supported. Version-1 board backups stay compatible.

Only standard GitHub-hosted public-repository runners are used: macos-15 arm64, macos-15-intel x64 and ubuntu-22.04 x64. Official actions are pinned by full commit SHA. The workflow runs only on pushes to platform-candidates (with an optional dispatch hook for future default-branch registration), has read-only repository permissions, does not create credentials or publish releases, and retains artifacts for three days. See [runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

Artwork is reused only from the already-published, owner-approved Windows v0.1.4 ZIP with its exact SHA256 checked. No source-site images are downloaded. Every extracted image is checked against the bundled sanitized inventory; existing local files are never silently replaced. The same game-art rights notices and DLMS/Omarchy MIT notices accompany candidates.

macOS targets are app ZIP and DMG, ad-hoc signed without a Developer ID identity, signing service or notarization. They are not trusted signed/notarized distributions; Gatekeeper and native owner acceptance remain pending. No system-security workaround is included. Linux targets AppImage; automated launch uses its supported extract-and-run mode under Xvfb, without changing kernel/AppArmor settings or passing --no-sandbox. FUSE mounting and validation on an owner's desktop/distribution remain pending.

A successful workflow artifact includes native-test.json describing the actual native-runner launch, secure renderer, writable per-user storage, editable target/Settings/theme behavior and real process relaunch persistence, plus checksums and a synthetic app screenshot. Binaries are staged only after smoke checks pass. Build success alone is not native user acceptance. Each candidate records its exact source commit; a candidate built after the Windows tag is not claimed to be that tag's Windows binary.
